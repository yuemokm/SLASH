# Slash：PM Agent 需求证据与功能取舍
日期：2026-10-02（Asia/Shanghai）

## 结论

更值得优先投入的是可交互原型及局部迭代、基于实际上下文的 PRD 编辑、真实资料的研究整理，以及简便的交付。持续上下文、准确性、版本与恢复是这些功能的基础。

独立评审中心、决策中心、大型关系图及暴露给普通 PM 的编排参数，目前不适合作为 Slash 个人版本的主打能力。建议合并、降低入口层级或暂缓扩展，而不是删除其有用的数据与约束。

以下是“公开证据＋用户已明确的 B 端工作场景＋现有代码”的产品判断，不是全球 PM 的统计优先级，也不是自动删功能方案。本次没有修改应用代码或配置。

## 检索方法与局限

- 使用 Exa Search 技能与 Exa 搜索、正文读取工具。
- 四个方向：从业者日常工作流；原始调查；失败与反对意见；中文/B端实践。
- 共 10 次搜索。请求结果数之和为 77，实际返回不保证达到请求数；合并后有 61 个不同候选 URL。候选页面不等于支持结论的独立证据。
- 正文核读包括两项调查、中文 PM 经验、负面体验和研究方法文章。对同一研究的镜像、转载和作者社交帖合并计权。
- 排除或降权厂商工具榜单、课程推广、无方法说明的惊人提效数字，以及只展示原型的黑客松项目。没有把厂商声称的功能直接当成用户需求。
- PM 研究主要是 GenAI 使用，不能直接推导全自主 Agent 的购买意愿。调查日期和人群也不同。
- 中文作者多为网名、自述工作经历；可用于理解具体任务和失败方式，不能用于推断人群占比或宣称真实提效比例。
- 没有获得足以统计 Reddit 社区意见的直接讨论样本，不宣称社区共识。
- “本次未找到高等级证据”不等于“没有需求”。

## 关键证据

### S1：微软 PM 混合方法研究

[Product Manager Practices for Delegating Work to Generative AI](https://www.maraulloa.com/pms_genai.pdf)

ICSE-SEIP 2026 论文，调查于 2025 年 4—6 月开展；885 名 PM，其中 735 名个人贡献者、150 名管理者；731 人同意遥测分析，另有 15 次访谈。

735 名个人贡献者可选最多三项用途：74% 起草/修改文档，53% 总结文档，32% 邮件/外部沟通，22% 用户研究或数据分析，12% 原型或代码。47% 担忧输出质量/不准确。150 名管理者中，51% 认为接入现有工作流困难。

含义：文档、资料整理、沟通有直接需求；准确性和工作流衔接不能省。数字来自特定公司和当时工具，不能当作所有 PM 的功能排序。研究也记录了希望自动化琐务、保留自身判断的差异。

### S2：Lenny / Noam Segal 调查

[AI tools are overdelivering: results from our large-scale AI productivity survey](https://www.lennysnewsletter.com/p/ai-tools-are-overdelivering-results)

2025-12-23 发布，1,750 名科技从业者包含 PM、工程师、设计师和创始人，不是 1,750 名 PM。PM 子组“最有价值用途”前三为 PRD、原型、沟通。原型未来意愿为 44.4%，研究的当前主要用途与未来意愿差距也大。

含义：当前生产价值与未来期待要分开；研究值得投入但还存在实现缺口。这是读者自选择样本和主观报告，本次取得的正文没有给出 PM 子组完整分母与所有题目设置，因此不把百分比解释为全体 PM 使用率，不与 S1 直接比较。

### S3：中文原型工作流

[Talen：先让 AI 出原型，点烂了再回头写 PRD](https://www.woshipm.com/ai/6447152.html)，2026-08-14。

作者自述先明确场景和范围，制作单 HTML 可交互原型，反复试用和局部修改，最后补 PRD。具体痛点包括没有行为的按钮、需求膨胀、版本混乱；也承认界面可能限制思考。属于单人实践，不能代表普遍最优流程。

含义：原型迭代、范围约束和版本辨识值得保留；允许从定稿原型辅助生成 PRD，不能从界面猜测未给出的后台规则。

### S4：PRD 失败方式

[产品包工头：AI 写 PRD 效率翻 3 倍但踩了 5 坑](https://www.woshipm.com/ai/6358792.html)，2026-03-19。

本文价值在具体失败模式：内容泛化、擅自扩大范围、缺真实业务和技术约束、遗漏异常场景。文中的倍数和“每份发现若干漏洞”未经独立验证，不采用作效果指标。

### S5：现场资料整理

[陈拉拉：当 AI 能秒出 PRD 的时候，我该焦虑么？](https://www.woshipm.com/ai/6372666.html)，2026-04-07。

作者自述政务项目中，将现场录音和笔记结构化后人工核对，强调实际工作与文档的差异。只采纳对资料处理流程的体验，不采纳文中关于 AI 永远不能完成某些任务的绝对判断。

### S6：对“PM 专用工具”的反对意见

[Daria Kasatkina：You Don’t Need an “AI Stack” as a Product Manager](https://hackernoon.com/you-dont-need-an-ai-stack-as-a-product-manager)，2026-08-02。

作者页面自述为 Tabby 高级 PM，认为通用 Agent 已可支持大量 PM 任务，重点在实际上下文与日常流程。她举例从沟通及会议记录中提取自己承诺的待办。属于明确的一手意见，不代表所有非技术 PM 的使用门槛相同。

### S7：研究分析的反面约束

[Product Talk：Customer Interview Analysis: Where AI Helps and Hurts](https://www.producttalk.org/customer-interview-analysis-ai/)，2025-10-08。

主张保留单个受访者的目标和场景，再做跨访谈归纳；资料浅薄时 AI 不能补出真实证据。作者提供研究教学服务，存在商业利益，作为方法论补充而非独立需求调查。

### S8：核对负担可能抵消提效

[DMZ：How AI tools for writing product docs fail](https://www.zumsteg.net/2026/02/05/how-ai-tools-for-writing-product-docs-fail-and-the-value-of-writing-yourself/)，2026-02-05。

作者报告生成文档看似接近完成，但偏题和事实错误难以检查，返工可能超过手写时间。这是个体负面体验，用于制衡仅看生成速度的结论。

### S9：大量 Agent 的维护问题

[Falk Gottlob：39 PM AI Agents Deployed: What Stuck, What Died, and Why](https://falkster.com/blog/39-agents-stuck-vs-died)，2026-04-27。

作者自述运营多个 Agent，认为明确触发场景、负责人和消费结果的位置比数量重要。所谓“孤立 Agent”部分依据站内引用数量，是弱代理指标，不能当作真实留存或活跃数据。只采纳范围膨胀和无用通知的失败案例，不用其数量决定 Slash 优先级。

## 对 Slash 的功能优先级判断

| 优先级 | 用户能感受到的功能 | 实际应交付什么 | 证据与判断边界 |
|---|---|---|---|
| P0 | 交互 HTML 原型与连续修改 | 从需求生成可运行页面；点选局部修改；保留未改行为；可回看版本；导出 HTML/链接 | S2、S3；结合用户明确主任务，排在 Slash 第一 |
| P0 | 基于上下文的 PRD 编辑 | 读现有资料/模板/原型；按模块生成和修改；字段、规则、异常与验收具体；待确认内容不伪装事实 | S1、S2、S4 |
| P0 | 项目资料接入和复用 | 读取常用文件、截图与会议材料；自动选相关资料；可追溯原文；避免反复解释背景 | S4、S5、S6；属于贯穿主流程的基础，不需独立管理中心 |
| P0/P1 | 研究和需求整理 | 跨材料提炼问题、需求和矛盾；保留用户/场景差异；联网资料有出处和时间 | S1、S2、S5、S7；先做好上传/本地材料，再完善外部接入 |
| P1 | 会议后处理、变更说明与沟通材料 | 提取已确认事项/未答问题/待办；按实际改动生成说明或汇报；可编辑导出 | S1、S2、S6；不等于自建会议软件或自动发送消息 |
| 条件性 P1 | CSV/Excel 和产品数据分析 | 根据真实数据回答问题并展示口径/计算过程 | S1 的研究/数据分析为合并项，不能据此单独声称 SQL 需求占比；是否优先取决于用户日常数据工作量 |

保持不同起点：可以“逻辑明确→PRD→原型”，也可以“粗需求→原型试用→补 PRD”。不强制所有 PM 先走同一套长流程。

## 现有和规划功能的取舍清单

本表结合当前 src/Sidebar.tsx、src/App.tsx、src/SettingsModal.tsx、main/quality.ts 与 docs/feature-coverage.md。只做静态检查；没有本轮真实运行验收。

| 功能 | 当前判断 | 处理建议 | 要保留的部分 |
|---|---|---|---|
| 独立评审入口与评审管理页 | 当前个人版入口价值偏低 | 并入会话/成果里的“检查问题”“处理修改意见”；多人正式评审再强化 | 问题位置、对应版本、处理记录 |
| 独立决策中心 | 与会话中的待确认事项存在重叠 | 默认把待确认问题放回相关会话或项目摘要，暂缓扩成管理系统 | 来源、确认记录、已确定约束 |
| 大型影响关系图 | 优先级低于准确修改与检查 | 优先显示“这次涉及哪些文件/规则”的清单；复杂图按需 | 底层关联与版本失效检测 |
| 独立知识库管理体系 | 当前已有并入资源的方向，继续保持 | 不再增加重复入口或强制整理知识卡流程 | 项目资料、已确认规则、来源与有效性 |
| 独立流程图工作区 | 作为单独工作区可降低优先级 | 在会话生成/修改，在成果预览/导出；规范在模板中管理 | draw.io 生成、规范、源文件 |
| 模型路由细则 | 对大多数非技术 PM 维护负担较高 | 默认可靠模型与回退；保留简单切换；复杂配置放高级设置 | 用户模型选择、可用性检测、失败回退 |
| 子 Agent 层级、白名单、并行上限等 UI | 属于运行机制，无需普通用户日常维护 | 使用合理默认值；高级设置按需；在任务中显示实际进度 | 权限继承、取消、资源限制和可诊断性 |
| 共享锁租期等技术参数 | 普通共享使用不应要求理解 | 系统默认管理；显示冲突和可理解的处理办法 | 版本冲突检测、不静默覆盖 |
| 基础共享盘创建与连接 | 用户明确需要，保留 | 做好读写、连接状态和恢复；暂缓共享成员在线编辑等重型协作 | 原有固定格式邀请和盘符体验 |
| 飞书/钉钉/MCP 交付 | 用户明确需要，保留 | 完善已有渠道，优先常用目标，不铺大量新渠道 | 版本绑定、发布回执、未知结果核对 |
| 质量检查 | 重要，但不能只查格式 | 检查与任务相关的实际行为；结构性提示按文档类型适用；不以章节齐全代表业务正确 | 阻止错误目标/版本冲突等必要保护 |
| 版本、撤销、恢复 | 必须保留 | 变更说明更好理解，便于查看和回退 | 用户数据与工作连续性 |
| Plan/Build、权限、暂停取消、健康检查 | 必须保留基础能力 | 常用操作简单；内部状态按需展开 | 用户控制与故障处理 |
| 多人角色、审批流、实时协作、跨设备同步、插件市场 | 第四阶段规划，尚不适合当前主目标 | 暂缓；出现明确多人使用需求后再评估 | 兼容性，避免破坏未来扩展 |
| 调度和自动化 | 不能笼统判无用 | 固定高频任务可有轻量触发；暂缓通用自动化编排平台 | 已授权任务、可见结果与关闭入口 |
| 通用业务规则推演平台、复杂客户差异管理 | 上轮构思，不是已完成能力 | 先针对一个真实业务流程验证，暂缓大平台 | 已确认规则与必要边界检查 |
| 无差别自动长篇 PRD | 不值得作为主卖点 | 改为按模块生成、修改既有内容、补真实缺口 | 模板与结构帮助 |
| 动画、多主题等视觉扩展 | 不作为业务差异重点 | 已有可保留，停止持续扩充；优先可读性和布局稳定 | 易读、清晰反馈、可访问性 |

“减少入口”和“删除数据/底层服务”是不同的操作。本报告未授权也未执行删除。

## 建议产品形态

主要入口集中到会话、项目资料、成果预览与交付。模板、连接、模型、共享配置作为辅助能力。检查结果和待确认事项应出现在用户当前工作的位置。

建议首先改善三个连贯场景：
1. 给一份既有 PRD 和页面参考，生成能点击的 B 端 HTML 原型，再只修改选定区域。
2. 给一组访谈、会议或现有系统资料，提炼带出处的需求，并询问关键缺口。
3. 在对话中修改业务逻辑后，更新对应文档与原型，给出实际差异、已检查内容和仍未知的部分。

新增功能不要求多一个导航入口。会议后处理、原型反推 PRD、局部交互验证可先作为会话动作。

## 验证方式

使用用户最近的真实任务，对照同模型、同资料、适当配置后的通用 Agent：
- 到可交付结果的人工操作与核对时间；
- 重复提供上下文的次数；
- 局部修改是否意外改变其他部分；
- 最终仍存在的业务/交互错误；
- 初次资料接入成本和后续复用收益。

不以生成字数、调用次数或“质量报告已通过”代替用户验收。功能删减先隐藏/合并入口并保留可恢复数据，再依据真实使用情况决定是否撤下实现。
