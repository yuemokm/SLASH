# Slash 参赛答辩准备

比赛要求：落地价值，以及与成熟 Agent 的区别；用户未提供其他评分标准或时长限制。本稿按约 3 分钟演示准备，可以缩短或延长，不声称这是比赛要求。

## 开场表达

Slash 面向需要反复核对业务资料、写 PRD、做交互原型并处理修改意见的 B 端产品经理。本次演示选取“机会门店新建”：资料分别来自流程文档、管理制度和字段表。我们关注的不只是生成一个页面，而是收到修改意见之后，能否保留依据、改对具体交互，并说明交付的是哪一版。

## 三个值得展示的区别

1. **规则与成果一起核对。** 字段必填、新增时是否展示、后续能否修改、是否仅正式落库，是不同问题。来源位置、适用阶段与待确认项分开保存，便于 PM 复核，不由模型把资料空白补成确定结论。
2. **原型真的运行。** 在受限浏览器里执行指定交互，保存预期、实际、截图和版本。失败可带回会话继续修改。检查只能证明列出的交互，不能代替业务负责人确认全部需求。
3. **修改后重新建立交付依据。** 局部草稿沿用 Pi 原生编辑能力；应用修改保留版本与差异。成果或依赖变化时，旧检查结果不能继续当成新版本的依据。

这些区别是产品流程与证据组织的选择。成熟 Agent 同样可能通过提示词、工具或扩展完成相关工作；本次没有与其他产品做同条件对照，不使用“别人做不到”或未经测量的提效百分比。

## 演示时怎么讲

- 先给评委看任务和实际成果，再解释资料依据，避免从系统架构和设置菜单讲起。
- 展示原有缺项：原型已有成功提交，但缺少服务失败后的恢复路径。
- 展示修订后的真实交互：开启明确标注的本地模拟失败，提交合法数据，输入保留；修改详细地址，旧错误清除；取消模拟失败，再次提交成功。
- 说明这经历了三轮真实模型局部修订与独立复验。最终 HTML 的 13 项独立检查和应用内 8 个场景通过，两套检查范围不同，不相加成“21 个业务需求全部正确”。
- 最后落到版本与尚未确认的问题。PRD 和约束对照的修订状态以最终交付记录为准，不因原型通过而称三份文件全部通过。

## 常见追问

**直接在通用 Agent 里描述问题，也能修改，为什么还需要 Slash？**

确实能改。Slash 要减少的是 PM 在不同地方手动维护资料来源、规则解释、文件版本、验收截图和交付状态的工作。价值不是独有的生成能力，而是让一次修改留下可以继续使用的依据。本次展示这一流程的实际行为，尚未量化节省工时。

**13 项都通过，能直接上线吗？**

不能这样推断。它们是本地 HTML 原型的具体交互检查。定位、编码和服务提交是明确的演示模拟，真实接口、后台规则及资料中的阶段冲突仍需确认与联调。

**检查会不会只是 AI 自己说通过？**

模型可以提出检查场景，宿主执行真实控件操作和断言，记录实际结果。本次还用了独立浏览器复核。用户确认的必检范围与成果版本绑定，不能通过删掉失败用例直接解除要求。业务规则的含义仍需人工核对。

**为什么使用 Pi？**

复用成熟的会话、模型调用、上下文压缩和编辑能力，避免自己再做一套。Slash 主要承担 PM 资料、权限、草稿、版本、业务依据和交付检查的组织。

**为什么有些模型任务仍会中断？**

真实实验出现过单次输出达到上限、任务超时。应用明确保留中断状态和已完成工作，不把未提交的修改算成成功。局部修改已在本次 HTML 修订中实际完成；更复杂文档修订仍须按最终记录说明限制，不能声称已经解决所有模型稳定性问题。

**下一步最值得做什么？**

先用同一类真实 PM 任务积累修改成功率、人工核对时间和遗漏项数据，验证不同模型的稳定性；再根据实际数据改进资料定位与跨成果一致性。暂不靠增加团队中心、插件市场等菜单来证明专业性。

## 演示前准备

- 使用已验证的便携版本或录制好的视频；提前打开 PPT，确认中文字体和视频可播放。
- 如现场演示原型，使用演示副本与合成输入，保持“本地模拟”标注。不要现场改写用户原始资料。
- 准备本地文件作为网络不稳定时的演示替代；不得用预录片段伪称现场生成。
- 不展示账号、密钥、完整内部文档或真实客户信息。参赛材料只保留说明问题所需的片段。
- 比赛获奖取决于评审及其他作品，本稿用于清楚展示实际成果，不保证名次。
