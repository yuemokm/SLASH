# Slash 比赛演示与业务验收准备

更新：2026-10-05。目标是让评委看到 B 端 PM 的真实工作闭环，而不是用菜单数量证明专业性。用户已明确：需要有落地价值，最好与市面上成熟 Agent 有区别；没有其他评分标准，需制作 PPT 和演示视频。演示时长未限定。下列为内部验收安排，不是官方评分或获奖承诺。

## 已确认的比赛交付要求

- 产品价值：围绕真实 PM 的资料理解、业务规则、原型/PRD、评审修改和交付，证明能完成具体工作。
- 差异方向：在现有成熟 Pi 能力之上，将业务依据、成果版本、实际交互验收和修改证据连起来。不能未经对照测试声称通用 Agent 都做不到，也不以另造 harness 或增加菜单作为差异。
- PPT：以实际问题、工作过程、前后成果和证据解释价值；准确区分已实现、已验证、仍待确认。
- 演示视频：使用实际应用和本轮真实成果录制关键操作；如压缩等待时间需明确标注，不伪造生成过程、完成状态或发布链接。
- 演示素材采用实际验证范围；最终 PPT、视频与答辩材料保存在 `deliverables/competition-2026-10-05`，不得将局部检查结果扩大成全部业务自动通过。

## 演示主线

围绕同一个“机会门店新建”任务，展示从现有资料到成果，再到修改依据的全过程。原始资料来自授权的 slash test 项目，演示使用副本。

1. **读取真实业务资料**：Word 流程与制度、Excel 字段表。明确本次读到了什么、哪些仍未知；字段必须关联具体工作表，避免把终端网点规则误用于机会门店。
2. **生成可以评审的成果**：一份模块 PRD、一份带交互的 HTML。编码展示与可编辑、正式落库与新建必填分别处理，模拟后台行为要有说明。
3. **解释设计依据**：从成果定位到关键规则和原文。是否允许变更不能靠模型一句“检查通过”，须能看到具体来源和落实位置。
4. **处理一次实际变化**：在演示副本中改变 Excel 的规则，旧提取文本不变。系统提示依据已经变化，保留旧版本，回会话重新读取并提出成果修改。
5. **交付与追溯**：核对版本差异、待确认问题和交付清单。没有真实配置渠道时只交付本地文件，不演示虚假的在线发布成功。

这五步只有在真实模型完成并通过业务核对后，才能连成正式演示。当前自动测试、合成回复或测试 PRD 不得替换第 2 步冒充模型能力。

## 真实模型必须通过的验收

详细来源和判断预期以 [机会门店业务场景](pm-business-acceptance-scenario-2026-10-05.md) 为准。

- 同一个完整任务能生成 PRD 和 HTML，任务结束状态与实际文件一致。
- 核对关键规则的满足、违背和未知数量，不以模型自评代替判断。
- 实际点击新建页的校验、成功、重复和失败分支，确认模拟行为不冒充真实接口。
- 用户提出与资料不同的新要求时，能区分旧依据和本次要求，解释具体影响并修改正确位置。
- 原始资料发生变化后，重新提取、修订成果、保留旧版本，能够查看前后差异。
- 核验来源路径、读取内容、草稿提交和恢复记录；全程保持原件只读。

耗时和返工次数应从真实任务记录获得；尚无有效数据时不使用“效率提升百分比”。可以在相同输入和验收条件下与现有人工流程做一次对照，说明差异及局限，而不是展示不同难度的任务。

### 首次真实模型基线：中断与业务缺项

2026-10-05 实际调用恢复的 Baishan 模型，经真实 Service/Pi 工具链读取资料并生成 7637 字 PRD 草稿。生成阶段耗时 276760 ms，随后模型返回 `length`，Run 正确保存为 `interrupted / model_output_limit`，未将未完成的 HTML 工具调用判为成功。三份原件、处理副本及提取文本的哈希均保持一致。完整记录：`.test-data/pm-business-real-2026-10-05T06-28-41-722Z/result.json`。

这次失败是单次输出达到上限，不能把它描述为上下文管理失败；Pi 原生压缩不能保证单条超长工具参数完整生成。下一步验证现有 `resumeRun` 的实际恢复效果，保留首轮失败记录，不自动调高未经核实的模型限额。

PRD 草稿初审发现四处实质缺项：没有明确编码和名称的后续变更限制；没有独立处理“仅正式落库”与“新建必填”；后台导入与上线阶段的来源冲突未列入待确认；将不可调整的定位地址与可编辑的详细地址混写。正确工作表、编码格式、名称长度等已体现在草稿中，但仍不能将该成果标为通过。HTML 交互及修改闭环尚未验证。

同一会话执行一次真实 `resumeRun` 后成功完成，Pi 原生上下文压缩实际触发且成功，PRD、HTML、约束对照三份文件已应用并保存版本。三份原件、副本与输入未变化。完整证据及仍存在的业务缺项见 [真实业务基线](real-model-business-baseline-2026-10-05.md)。恢复成功证明运行链路有效，不撤销首轮失败或将内容质量标为通过。

随后实际操作最终 HTML：13 项通过、1 项失败、1 项待验证；缺失的是提交服务失败模拟路径，编码修改后的差异尚未执行。HTML 两种地址的编辑边界正确，而 PRD 表述仍不一致，后续需要修复跨成果一致性。现阶段不能将该任务用作“完全自动、无需复核”的演示。
