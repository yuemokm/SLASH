# 工具授权状态与完全访问

关联需求：F03 / F19、PF03 / PF05 / PF09。当前范围：修复授权历史卡片误显示、失效点击和会话删除后的状态脱钩。

## 问题与根因

`state` IPC 返回的 `pendingApprovals` 实际包含授权审计历史。会话原先只按会话 ID 过滤，已允许、拒绝、取消或过期的记录仍显示“Agent 正在等待确认”和授权按钮。新任务选择完全访问后，也可能看到同会话旧任务的历史卡片；点击会触发 `APPROVAL_NOT_PENDING`。

另一个状态问题在会话删除：删除函数替换授权记录数组，而 Broker 仍持有原数组。之后新增授权无法通过当前 State 正确持久化或呈现。删除现在原地移除该会话记录，保持共享数组身份；其他会话的审计历史不变。

## 权限与生命周期契约

Run 创建时保存权限模式快照，继续任务继承旧 Run 的模式。完全访问跳过能力策略中的 ask；明确 deny、Plan 只读限制、目录授权、原件保护和版本检查仍生效。自动接受仅跳过普通成果编辑的 ask。

界面仅把状态 pending、对应 Run 正在运行且未过截止时间的记录视为可操作。返回的历史记录保留终态，不再作为等待卡片。授权按钮以同步锁防止双击，处理后按服务返回的实际结果显示提示，并重新加载状态。

Broker 在改变持久权限前核对真实 waiter、Run 活跃状态、截止时间、Plan 与明确 deny。旧页面迟到的“允许并记住”不改变权限、不重新派发。重复或冲突决定返回原终态与友好提示；已移除的 ID 返回 `APPROVAL_UNAVAILABLE` 与“刷新任务状态”说明。终态返回兼容原 `ApprovalRequest` 字段，并增加 `outcome` / `message`（`shared/approval.ts`）。

取消、Run 结束及应用关闭结束等待并中止正在执行的受控进程。应用启动将遗留 pending 标记为 expired，不重放工具。设置能力为 allow 时唤醒真实等待；改为 deny 时拒绝，旧按钮不能恢复授权。

## 验证与边界

`tests/approval-lifecycle.test.ts` 覆盖完整授权模式全部 ask 能力、新 Run 保存模式并正常执行、明确 deny / Plan / 只读目录、真正标准审批、重复和冲突决定、取消先后竞态、超时回调尚未运行的截止判断、重启旧记录、设置权限变化、删除会话后数组身份与持久化、项目切换后隔离。现有 `agent-mode.test.ts` / `pm-workflows.test.ts` 保留 Plan 确认、来源复核和恢复测试。

这些测试使用临时项目和合成 Runtime，证明权限与生命周期契约，不宣称真实模型、外部写入或系统级沙箱验收。对本机已知默认/旧开发 profile 的只读元数据检查没有近期 Run；没有据此确认用户截图对应的具体 Run。未读取密钥、消息正文、输出或原始推理，未修改用户数据库。

主进程授权修改需要重启开发命令或新版应用；不会自动恢复旧审批等待。对应流程源文件为 `diagrams/tool-approval-lifecycle.mmd`。
