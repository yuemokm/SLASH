## 本轮目标

0.3.10 已能执行具体原型交互并保留失败证据。下一步用真实机会门店资料核对并修订 PRD、原型和约束对照，而不是把测试通过数当作业务正确率。旧基线、失败记录、原始资料和既有交付包保留。

已观察到的效率问题是 `write_draft` 要求完整文件：即使只修改一段交互，模型也要重发 25 KB HTML。此前真实任务已出现单次输出截断。因此本轮优先复用已安装 Pi 的 `createEditToolDefinition` 与可注入 `EditOperations`，把成熟的匹配和差异实现接到 Slash 的待应用草稿，不新增编辑引擎或上下文压缩器。

## 不变约束

- 所有修改从会话发起；模型不能直接覆盖成果或参考资料原件。
- 增量修改保留实际文件的原始版本哈希，最终应用沿用既有 ChangeSet、文件冲突和版本备份。
- 同一文件的连续修改必须基于最新草稿，旧哈希和并发覆盖应明确失败。
- Plan 不允许修改，目录和能力授权在读取及提交草稿时核对；取消不留下已被当作成功的新草稿。
- Pi 负责文本匹配、编辑差异与上下文；Slash 负责授权、草稿身份、版本及来源证据。
- 真实业务实验使用新的独立 `.test-data` 项目；不重跑旧恢复请求、不改真实 `slash test` 或旧基线。

## 增量编辑验收

1. 对已应用文本生成局部草稿，不改变磁盘原文件。
2. 同一 Run 连续两次编辑，第二次保留第一次修改；复用待应用卡片，避免可误应用的旧草稿堆积。
3. 每次指定宿主返回的内容哈希；重复、重叠、找不到的匹配按 Pi 实际行为报告，旧哈希或正式文件变化拒绝提交。
4. 草稿读取分页并明确总量和未读范围，实际 Pi 差异有界返回。Pi 可进行空白及排版规范化匹配，因此匹配成功不等于业务语义正确。
5. Pi 内存编辑结束后，再核对当前授权、模式、取消信号及版本，最后同步登记草稿；宿主不通过 Pi 默认文件写入操作落盘。
6. 原件、未授权目录、无效 UTF-8、二进制及需要专用工具管理的文件拒绝编辑。历史应用与恢复继续走已有版本流程。
