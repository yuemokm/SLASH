# 模型请求中止的错误保真

日期：2026-10-06。关联 F19（任务与恢复）；本轮只修复错误报告，保留 Pi 原生上下文、压缩、重试和既有任务预算，不重放真实项目任务。

## 已证实的历史记录

`agent/sessions/2026-10-04T12-33-26-291Z_01a106e7-a308-7643-9650-cdb741049bc5.jsonl` 的 2026-10-05T12:12:02Z 助手记录为 `stopReason=aborted`，并含 `OpenAI Responses stream ended before a terminal response event`。这条记录中的写草稿调用未完成，不能把流中的候选调用视为已执行成果。

已安装 Pi 的 Responses 解析器在缺少终态事件时抛出该错误；适配器随后根据请求 AbortSignal 是否已中止，把结果标为 `error` 或 `aborted`。因此，仅凭这句话不能确认是供应商、代理网络、用户取消或宿主截止时间中的哪一方触发。本次历史记录使用 10 分钟任务预算；到期由 Service 记录 `TIME_BUDGET_EXCEEDED`，手动停止由 Service 自己的取消状态识别。后续复杂任务真实续作证据促成默认预算调整为 30 分钟 / 120 次工具，详见 [2026-10-07 有界宿主预算](runtime-limits-2026-10-07.md)，旧任务记录与时间不变。

原实现的 `assertRuntimeSucceeded` 把所有 `aborted` 统一转成 `CANCELLED: 模型请求已中止`，丢失 Pi 提供的具体错误。Service 虽然仍把没有宿主取消记录的此类任务标为 `failed`、允许显式继续，但用户只能看到笼统中止文案。

## 本次报告的边界

上述会话文件在 2026-10-06T09:56:50Z 出现用户“继续”输入。所读默认 profile 数据库只有旧状态，未与当前开发应用和该会话记录吻合，因此改用真实窗口状态与原生会话记录交叉核验，没有修改数据库。北京时间 18:04，今天 17:56 的任务 `515c14fe` 仍在生成；界面尾部的“应用在任务运行期间退出”卡片实际对应 2026-10-05 20:04 的旧任务 `8913ea11`，并非今天这轮任务。

最终确认本次真实执行顺序：

- 17:56:50（09:56:50.609Z）：用户发送“继续”。
- 18:02:35（10:02:35.996Z）：Pi 助手消息 `stopReason=error`、`errorMessage=terminated`，包含尚未执行的 `write_draft` 候选；响应没有正常完成。
- Pi 自动重试，真实界面继续显示正在生成，并未在此时宣告任务成功。

因此，本次直接终止原因是宿主十分钟预算，之前存在一次响应流 `terminated`；不能据此进一步断言是上游服务、网络或代理中的哪一层造成。两个失败响应的 usage 均为零，表示未收到正常用量回执，不能视为没有发生调用或费用。候选工具参数并不构成已保存草稿；没有执行它们来补造成功。旧中断卡放在最新回复之后的 UI 排序缺陷另行修复。调查未重启用户应用、重放真实任务或改动业务资料与模型配置。

## 实现

- `main/agent.ts`：未被宿主取消路径拦截的 Pi `aborted` 结果返回 `MODEL_RESPONSE_ABORTED`，保留其 `errorMessage`；没有详情时只报告请求已中止。`error`、`length`、完成状态及原生压缩机制保持既有处理。
- 真正用户停止仍由 Service 的取消集合和 prompt 的 AbortSignal 桥接处理，终态为 `cancelled`；任务超时仍保留宿主截止原因。错误在 Service 原有脱敏路径后保存。
- 已生成回复、待应用草稿和检查点保持原有恢复方式；没有发起新的真实任务、自动续写或补执行流中的写工具。

## 同日再次失败的协议核对

2026-10-06 再次只读核对同一 Pi 会话的消息元数据（时间、协议、停止原因、用量和工具名称/内容长度），未读取或重放用户业务正文。最近一次用户输入时间为 `10:24:44.192Z`。`10:24:52` 至 `10:26:44` 的 Responses 读取工具消息正常完成；`10:32:32.080Z` 的 `write_draft` 候选包含 23,027 个内容字符，消息为 `error`，错误为缺少 Responses 终态事件；`10:33:19.467Z` 后续消息为 `aborted`，同样保留该错误并包含 253 字符的未确认写入候选。仅凭会话元数据无法确定后一次中止是否由用户或宿主触发，不能直接套用上一轮十分钟预算的结论。

同一会话 `10:22:27.780Z` 已有正常完成的 Responses `write_draft` 工具消息（15,699 字符、6,024 输出 token），其他读取工具也收到正常用量。因此这里不是已经证实的“Responses 协议完全不受支持”。此前隔离真实测试若只走旧配置迁移后的 `openai-completions`，也不能证明用户当前选定的 Responses 链路通过。

[白山官方 LLM API 文档](https://ai.baishan.com/docs/docs/llm-api.html#responses-api)明确提供 `POST https://api.edgefn.net/v1/responses`，并以 `DeepSeek-V4-Flash-0731` 展示请求。该文档不能证明任意长工具响应均正常结束，但足以排除按模型名猜测并静默改用另一协议的做法。

已安装 `@earendil-works/pi-ai` 的 `dist/api/openai-responses-shared.js` 只有收到 `response.completed`、`response.incomplete` 或 `response.failed` 才确认终态；普通 EOF、`[DONE]` 或单个工具项完成均不能代替完整响应的终态。解析失败时 Pi 返回 `error`，若请求信号同时已中止则返回 `aborted`。候选工具参数即使看似完整，也不能在这种结果下补执行；上游的 `response.incomplete` 且原因 `max_output_tokens` 才可确认为输出上限，而缺终态不能猜成 `length`。

Pi 默认 HTTP 空闲超时为 300,000 毫秒，按网络空闲计时；Service 仍有总任务 600,000 毫秒预算。一次长工具生成耗时较久不是空闲超时的充分证据，缺终态错误也不能独立定位到网络、上游代理或本机截止时间。当前不修改用户 profile、接口协议或超时设置，不跳过终态检查。进一步验收使用隔离项目、当前显式选定的同一协议与真实 Service/Pi，区分真实调用完成、浏览器交互验证和失败恢复；结果由主线程单列记录。
