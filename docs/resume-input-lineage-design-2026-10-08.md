## 已确认的问题

`main/service.ts` 的 `send` 将传入文字保存为 `run.input`，同时保存带 `runId` 的用户消息；宿主显式恢复才写入 `resumedFromRunId`。这些身份已存在，无需通过文字标记识别恢复链。

修复前 `resumeRun` 按 `startedAt` 查用户消息，找不到时取时间大于等于开始时间的最后一条消息。它未优先使用消息 `runId`，可能选中后来的补充或另发任务。该消息文字又作为“原任务目标”加上恢复说明后传给 `send`。所以恢复 Run 的 `input` 是整段恢复包装，并非干净的原任务。连续恢复已观察到文字长度 1399 → 2198 → 2997，包装标识 0 → 1 → 2；目标仍在，但重复累积。

## 已实施的最小改动

在现有 Service 内增加 `resumeOriginalInput` 与 `resumeInputMessage`，由原 `resumeRun → send` 路径使用，不增加请求器或按文字剥离的规则：

1. 从待恢复 Run 沿明确的 `resumedFromRunId` 找无恢复父节点的根 Run，防循环并检查同会话、模式、权限及已有项目范围。祖先的 `resumable` 已被成功创建子 Run 的操作设为 false，不能把它误判为输入来源失效。
2. 根 Run 优先读取已有 `input`；缺失时按用户消息 `runId` 精确匹配。旧无消息身份数据仅允许唯一且时间恰好等于根 `startedAt` 的用户消息；不能用 `>=` 猜测输入，不能忽略冲突的明确身份。
3. 每次组成一份恢复说明、根原目标及待恢复 Run 自己的最新真实检查点。保留当前部分回复上限、已成功工具记录和 `resumeDraftMetadata(previous)`；不再嵌入祖先检查点或恢复包装。
4. 父 Run 缺失、循环、跨会话/模式/权限/项目或输入来源不唯一时，保守停止本次恢复，保留旧数据并说明原输入无法核实，可由用户另发明确任务。不能把可疑包装冒充已验证原始目标。

兼容边界：历史 Run 缺 `input` 时才查消息；有可信 `input` 时不因消息文字冲突改选目标。缺模式/权限字段仍沿用既有 Build/standard 默认；manifest 缺失可兼容，但不能称项目范围已验证，存在则检查。显式父 ID 找不到会报错；历史根本没有 `resumedFromRunId` 的 Run 只能以自身为根，不能通过 `attempt` 或包装文字猜出旧根，已有包装原文也不会被剥除。该限制不构成修复所有历史坏记录的承诺。

普通手工新发任务没有恢复父身份，应成为自己的根，即使文字中出现“继续”或旧包装也不能据此追溯旧任务。现有仅对无附件、无 workflow 等条件下的精确“继续”“继续任务”分派恢复入口，保持既有边界。

## 必须保留的约束

- 本轮 workflow、附件、模型、思考档位和权限继续从待恢复 Run 继承，不能用更早根 Run 扩大当前授权。附件缺失时只能使用精确属于待恢复 Run 的消息附件；workflow 来源仍按现有执行路径重新核验。
- 保留 `assertResumeParent`、未完全退出检查、结果未知的外部/数据库操作阻断、草稿归属与版本检查。Plan 仍只读，不能因找回原目标增加工具权限或重放成功写入。
- 保留验收合同已有请求、输出、基线和追加输入历史。`run.inputs` 中已交付输入及现有原生会话继续保留；不自动重发 queued/unknown 输入。新恢复说明不能以“原目标”为由抹掉后续已交付的纠正要求。
- 使用上一轮最新检查点，不代表祖先成果或记录被删除；仍可通过真实草稿、操作和合同核对已有进度。不得把部分回复当作已提交成果。
- 本增量只阻止后续恢复输入继续嵌套。既有 Pi 历史仍保留，**不能宣称清除了历史重复内容或历史 token**，也不能承诺恢复必然成功。
