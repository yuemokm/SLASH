# 业务验收登记缺口：后续设计

状态：只读代码审计及待实施建议，不代表已开发。当前真实评审修订任务运行期间，生产源码、构建与启动脚本保持冻结。

## 已确认的缺口

`Service.beginTaskAcceptance` 保存原请求；`taskSourceRead` 保存实际阅读回执；`registerTaskChange` 绑定成果版本，并添加 HTML 加载/运行/截图检查。PRD 的来源选择、假设和覆盖映射依赖模型调用 `define_task_acceptance`。因此真实 QE12 的 24 条读取与 25 条字段证据可以与合同三类登记均为空同时存在。

独立内容审查仍读取合同来源及 Run 的阅读回执，不能说这些资料完全没有进入审查。问题是审查输入与成果依据登记是不同职责，前者不会自动补齐后者。

`TaskAcceptanceDomain.validate` 当前把检查引用的 requestIds 计为已映射，自动 `host:render` 引用全部请求，可能使 unmappedRequestIds 为空。businessCoverage 仍为 unverified；不能据此把页面烟测当作业务覆盖。

首次任务没有已确认或前轮验证用例时，baseline 为空符合现有规则。不得为了消除空值而生成虚构基线。

## 最小实施方向

1. 在现有检查报告中增加宿主生成的登记缺口投影，区分真实读过的版本、明确选为成果依据的来源、候选业务覆盖。复用 sourceId/readId，绑定合同、输出版本和读取列表。未登记假设明确为“尚未登记”，不表示不存在假设；不把全部 reads 自动加入来源，不合并字段证明。
2. 自动页面烟测只计结构检查，不消除业务映射缺口。摘要和已有质量折叠区展示，不新增独立管理页面；普通聊天不触发。
3. 本轮仅做宿主确定性审计，不默认增加模型调用、Run 状态或补登记阶段。实际任务已出现多次上下文整理，额外调用可能令已生成草稿的任务再次超时。保持执行结果、已有草稿、登记缺口和业务确认四者分离；缺口不自动触发修稿、不收紧保存权限，也不放宽既有发布门禁。
4. 普通会话不必选择工作流才能识别真实参考材料。依据已授权资源角色、参考根及已核验的原件提取链分类；先排除成果依赖、技能和宿主索引，身份不足明确为未知，不静默当作不适用。选用与候选业务映射仍由模型显式登记，宿主不能替它编造依据。

同 Pi 自动补登记保留为后续备选，尚未实施或验证。后续是否引入应依据正常生成耗时和实际缺口收益判断，不能仅为填满字段增加自动请求。详细边界见 `.test-data/task-registration-gap-proposal/PLAN.md`。

## 验证边界

确定性检查涵盖读取与选用分离、来源变化和撤权使登记过期、烟测不消除业务缺口、无工作流参考材料、零新增模型调用及普通聊天不受影响。旧要求、成果哈希和原检查状态不变，旧报告未记录审计不能解释为没有缺口。规则含义、业务对象和来源冲突效力仍需语义核对，登记完整不等于内容正确。

通俗解释：软件已经记录“看了什么、做了什么”，接下来要明确“做出的结论依据什么”。补不齐就显示未核对，不能用页面能打开代替业务正确。
