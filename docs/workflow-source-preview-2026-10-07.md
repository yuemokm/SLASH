# 工作流来源预览与按需续读（2026-10-07）

普通工作流首次提供有界正文预览：每来源最多 **4000 UTF-16 字符**，各来源正文累计最多 **16000 字符**。这些是预览字符上限，不是供应商上下文容量或 token fit 保证；来源定位、JSON、用户输入、系统提示、工具 schema 和后续工具结果另有开销。没有新增 tokenizer、独立预算系统、压缩循环或自动重发。

来源仍经过原有授权、只读读取、版本与文件变化核验。回执保存完整来源/所选版本 SHA256、总 characters、实际 includedCharacters、truncated 和读取时间。原件没有因预览缩短而被截断写回；只提供片段也不能被称为完整语义核验。

对当前版本且真实有正文的部分来源，宿主在工作流 JSON 中附 nextRead：

~~~json
{"mountId":"真实授权目录ID","path":"实际来源路径","characterOffset":4000,"characterLimit":12000,"expectedContentHash":"完整提取正文的SHA256"}
~~~

模型可将 nextRead 原样传给已有 read_file。characterOffset 是 0 起算 UTF-16 字符偏移；read_file 的 offset/limit 则是 1 起算行分页，两者不能混用。字符分页继续由现有读取工具复核授权、文件 hash、取消信号和来源回执。总预览预算用完后，后续来源正文可能包含 0 字符，nextRead 从 characterOffset=0 开始，明确没有提供该正文。

普通文本原字节和提取正文 hash 通常一致。Word 原件与提取正文不同：来源回执 contentHash 继续绑定 Office 原件字节，nextRead.expectedContentHash 绑定提取正文，符合 read_file 字符分页的真实校验逻辑。已登记的 metadata_only 处理副本没有已提取正文，不生成假的字符续读建议。历史版本预览不给指向当前文件的 nextRead；提示它仍是所选历史版本的部分正文，不能用当前文件冒充历史续读。短源或恰好全部包含的来源不附 nextRead。

change_summary 的真实旧→新内容读取、确定性 diff 和原有差异限制保持原行为。来源预览修改没有改变 Pi 的计量、原生压缩阈值、近期保留配置、有限恢复、供应商重试、模型限额或权限。

## 已登记 Excel 提取资料的目录首包（2026-10-08）

工作流可通过宿主回调识别**已登记、已应用、当前版本的内置 XLSX 提取 TXT**。成功时首包提供真实工作表名称、可见状态、行列范围和来源身份，并提示使用 `locate_spreadsheet` 选择工作表和按需定位行；不再为这份来源任意截取前 4000 字正文或默认建议连续续读 12000 字符。首次目录页不一定包含全部工作表：目录未完时携带宿主生成的 `nextCursor`，继续查询须保留完整游标，不能跳过尚未返回的条目。

目录完整 JSON 和其定位指引共同扣除原有每来源 4000、总计 16000 字符预览预算；回执、工作流说明等既有开销仍另计，不表示整个供应商请求只有 16000 字符。工作流把实际剩余预算传给宿主；宿主按预算返回完整条目和正确游标，工作流不截断 JSON 或自行裁切工作表。目录可用预算不足 1500 字符时跳过目录回调并保留原有限正文预览，避免将本可读的普通 TXT 清零。

目录回执记录 `contentStatus: spreadsheet_catalog`、完整提取 TXT 的 hash 和总字符数，但 `includedCharacters: 0`、`truncated: true`。即使所有工作表名称已列出，也没有读取完整正文；导航 `fullBodyRead: false`、`bodyCharactersIncluded: 0`、字段关系未核验、业务语义未确认和 `humanConfirmed: false` 保持。目录不是字段证据，不能直接用于证明某业务阶段允许编辑或展示。

未登记 TXT 的文字即使自称某个工作表也不能成为宿主目录证据；回调返回不适用时沿用普通预览，不向会议或制度 TXT 附无关的 Excel 警告。当前来源 hash、目标或权限变化、取消及无效目录响应直接失败，不伪装成可用 fallback。历史来源和 `change_summary` 不调用当前目录回调，继续保留原历史片段及确定性差异行为。

验证覆盖真实隔离项目的 XLSX→登记副本→内置提取→仅应用隔离输出→工作流目录，以及未登记诱导 TXT、原件字节不变、分页不跳页、目录 JSON 总预算、普通 TXT 低剩余预算兼容、权限/取消/版本拒绝和历史/diff 不变；这是本地来源与读取机制验证，尚不表示真实模型一定会选对业务对象。

通俗解释：对于应用确实处理过的 Excel，先给模型一本“工作表目录”，帮助它找到正确的表，再让它读取需要的行。目录不是表格正文，更不是业务结论；普通文字资料仍按原来的方式阅读。

## 真实失败与修复边界

C 新分析 Run 4cd727b8-5a91-4ee5-bbf7-a360da487b30 复用既有三份可写成果；原始歧义要求是只分析、不修改文件。旧执行先注入较长工作流正文，模型随后错误地将 includedCharacters=32000 作为 read_file 行 offset；真实提取文件只有4036行。此工具失败之后，上游响应 stopReason=length，usage.output=1。不能把这两个相邻事件认定为供应商的唯一根因，也不能说已用完12000输出预算。

## 验证

正式专项包括原工作流兼容性与六项新增回归：多来源4k/16k正文预算、真实 nextRead执行及行/字混用和版本冲突拒绝、短源无nextRead、metadata_only、真实Word的双hash绑定、历史版本与change_summary差异。接入后类型检查、构建与有界并发全量591/591测试通过。默认并发首次有一个测试文件进程退出，原日志保留，确切原因未知；未修改断言凑通过。

真实复测 Run `da8a4435-13e6-4491-a8b9-1d64a8a28e8b` 自然结束，用时588024ms。首次用户消息由48868降为13225 UTF16字符；模型实际用characterOffset=4000/characterLimit=12000续读fields和policy，没有再把字符数当行号。它未原样携带nextRead的expectedContentHash，因而不能声称完整照用了全部参数；宿主另行核验了来源读回执和冻结版本。Pi原生压缩完成两次，0修改/0ChangeSet，三个已有成果的字节和版本数保持。测试应用正常关闭，783项保护记录hash不变。

模型确实给出范围澄清问题，但仍混淆创建输入与后续变更权限，引用错流程行号；本次只证明运行路径修复与不写入约束有效，不证明业务分析完整正确。完整证据见[后续实测](quality-real-followup-2026-10-07.md)。

通俗解释：先给模型短资料预览，再告诉它正确的“从第几个字继续读”。需要更多内容时，它仍通过原来的正式工具读取完整资料，不把短预览假装成已经读懂全部文件。这能避免本轮已复现的续读用错单位，也能减少第一次请求里的资料体积，但不能承诺任何未知模型都装得下所有后续内容。
